Основание: `AUDIT_MAIN_FUNCTION.md` и материалы `audit/`. План подготовлен 20.09.2026. Задания ещё не выполнены.

## Как пользоваться

Выбрать рекомендуемую модель в Codex и отправить:

> Прочитай CODEX_TASKS.md. Выполни только задание T01, соблюдая общие ограничения. Проверь зависимости и критерии приёмки. Остальные задания не выполняй. В конце перечисли изменения, проверки и оставшиеся ограничения.

Для следующего задания заменить номер. Модель не нужно добавлять в приложение: здесь выбирается **модель-разработчик в Codex**, а не платный AI-сервис для каждого пользовательского запроса. Эти задания можно выполнять последовательно в текущем проекте; создавать отдельную задачу для каждого не обязательно.

| Astra / `gpt-6-astra` | Сложные неоднозначности: достоверность данных, распознавание INCI, архитектура экспертных правил, персонализация, независимый аудит | high; xhigh при неразрешённых противоречиях |

Официальное позиционирование: Terra балансирует возможности и стоимость; Sol предназначена для сложной профессиональной работы; Astra для наиболее сложных сквозных задач. Источник: [OpenAI Models](https://developers.openai.com/api/docs/models). Конкретное распределение заданий ниже является инженерной рекомендацией, а не сравнительным тестом этих моделей на данном репозитории.

«Astra» не означает, что Sol принципиально не справится. Здесь дополнительное внимание оправдано риском неверных рекомендаций. Высокая мощность модели не подтверждает медицинскую корректность: экспертные сведения и ограничения должны иметь проверяемые источники и предметную проверку человеком.

Экономный вариант: Astra проектирует контракты и правила в T04/T10, Sol реализует T05/T14 по ним, затем Astra независимо проверяет результат в T19. Не включать max/ultra по умолчанию. Если Terra сталкивается со сменой контракта между модулями, передать это Sol, а не расширять локальное задание бесконтрольно.

## Общие ограничения каждого задания

1. Сначала прочитать текущие файлы, аудит и `git status`. Аудит фиксирует прошлое состояние: перед исправлением воспроизвести дефект заново.
2. Не переписывать приложение, не мигрировать фреймворк, не трогать авторизацию, Telegram, деплой и секреты. Не выполнять push/deploy. Не менять маршруты API; при необходимости расширять существующие данные обратно совместимым способом.
3. Не удалять и не откатывать существующие чужие изменения. Не делать `git add .` и общий коммит пользовательской работы. Работать небольшими проверяемыми изменениями.
4. Не подставлять демонстрационные товары вместо реальных. Не добавлять ингредиенты, источники, проценты, инструкции, результаты исследований и цены «из памяти» без подтверждения.
5. Новые платные API и отправку фотографий стороннему провайдеру не включать без отдельного решения пользователя. Ключи не сохранять в клиенте/репозитории; личные фото и сведения профиля не писать в диагностические логи.
6. У каждого исправления должен быть тест на исходную ошибку и нормальный сценарий. Для UI проверить реальные размеры элементов и клики, не только скриншот.
7. Запустить релевантные тесты и `npm.cmd run check`. Известные красные регрессии из T01 перечислять явно; к T19 они должны стать зелёными без отключения проверок. Проверка синтаксиса не заменяет проверку смысла отчёта.
8. Не переименовывать каждый отчёт в REPORT.md. Для завершённого задания создавать краткий `reports/Txx.md`: что изменено, что проверено, команды/результаты, известные ограничения. Если часть приёмки не выполнена, не писать «готово».
9. Не выполнять следующие задания автоматически. Указанные зависимости должны быть реализованы или явным образом согласованы перед началом.
10. Доменные ограничения и противопоказания не изобретать. При отсутствии достаточных данных показывать неопределённость, а не благоприятную оценку. Codex не заменяет косметического химика/дерматолога.

## T01. Регрессионные проверки

**Модель:** Terra high. Причина: известные входы и дефекты уже зафиксированы, не требуется придумывать экспертную логику.

**Задание для Codex:**

Прочитай аудит и сценарии `audit/`. Преврати ключевые воспроизведения в детерминированные регрессионные тесты с явными ожидаемыми результатами, отдельно для серверных функций и браузера. Не исправляй код приложения в этом задании. Не используй текущий ошибочный вывод анализатора как эталон.

Добавь случаи: Topicrem с 20 позициями; разорванный PEG-40; неоднозначный Hamamelis; мусорный OCR; INCI с числовой маркировкой в конце; `mode:unknown`; 503 при составе с анестетиком; замена товара A на B; только активы GIGI; точный EAN карточки без INCI; профиль по умолчанию; перекрытие сканера на 390 px.

**Приёмка:**
- Нормальные сценарии проходят, каждый известный дефект воспроизводится падающей проверкой с понятной причиной. Красные тесты запускаются отдельной документированной командой до соответствующих исправлений.
- Нет зависимости unit-тестов от интернета. Моки не обозначены как испытание реальной камеры/OCR.
- Существует матрица «дефект -> тест -> задание-исправление», без пропуска safety-случаев.

## T02. Отказ сервера не должен создавать ложный отчёт

**Модель:** Sol high. Причина: нужно согласовать обе точки запуска анализа, UI и историю.

**Задание для Codex:**

Устрани автоматическую подмену серверного анализа вызовом `localAnalyzeComposition` при HTTP/сетевой ошибке. Сохраняй введённый состав и фото, показывай понятную ошибку с повтором. Не выдавай оценки и советы, не сохраняй отказ как успешный анализ. Не создавай новую offline-экспертную систему. Проверь ручной запуск, запуск после OCR и повтор запроса.

**Приёмка:**
- 503, timeout и offline не превращают Prilocaine Hydrochloride в безопасный уход.
- Нет устаревшего успешного отчёта, визуально относящегося к новому неуспешному запросу.
- После восстановления API повторный запрос даёт серверный результат; исходный ввод сохранён.

## T03. Принадлежность состава товару

**Модель:** Sol high. Причина: асинхронные гонки и несколько способов выбора товара.

**Задание для Codex:**

Раздели поисковый текст и выбранную карточку. Свяжи текущий состав с конкретным товаром/источником. При смене выбранного товара или редактировании его поискового названия инвалидируй автоматически подставленный состав и старый результат. Не удаляй независимый ручной состав неожиданно: обозначай режим и при необходимости запрашивай подтверждение замены. Карточка без INCI не должна наследовать чужой состав. Запоздавшие ответы предыдущего поиска не применяются. Не выбирать первый неоднозначный результат автоматически при нажатии «Разобрать».

**Приёмка:**
- A -> название B -> анализ не отправляет состав A под B.
- Медленный ответ A не перезаписывает уже выбранный B; очистка поля отменяет устаревшие запросы.
- Два похожих продукта требуют выбора; ручной ввод и новый снимок работают независимо и предсказуемо.

## T04. Контракт достоверности

**Модель:** Astra high. Причина: от этого межмодульного решения зависят OCR, источники, анализ, UI и история.

**Задание для Codex:**

Введи минимальную общую модель данных в существующей архитектуре, без микросервисов и смены маршрутов. Сначала зафиксируй контракт в `docs/analysis-contract.md`, затем реализуй валидатор/адаптеры и контрактные тесты. Не переписывай всю систему в этом задании.

Предусмотри: идентичность товара; версию состава; источник и дату; `full/active_only/partial/unknown`; исходный текст; происхождение совпадения каждого ингредиента; подтверждённый/сомнительный/неизвестный статус; отдельные показатели читаемости OCR, идентификации и покрытия знаний; версию алгоритма; профиль, использованный для расчёта. Число похожести строк нельзя называть вероятностью правильного OCR. Сохрани совместимость текущих потребителей, но не маскируй отсутствие сведений значениями по умолчанию.

**Приёмка:**
- Неполный и полный составы различимы после прохождения всего серверного пути.
- Неоднозначное совпадение нельзя превратить в подтверждённое без явного изменения статуса.
- Отсутствие метаданных не означает проверенный полный INCI; `null/unknown` обрабатывается безопасно клиентом.
- Контракт определяет поведение для старых сохранённых результатов без переинтерпретации их как новых.

## T05. Очистка и нормализация без выдумывания

**Модель:** Astra high. Экономная альтернатива: Sol high по утверждённому T04 с последующей проверкой Astra.

**Задание для Codex:**

Исправь `inciCleaner` и его использование анализатором. Сохраняй исходные фрагменты и границы. Корректно обрабатывай запятые, точки с запятой, переносы и разделяющие точки, не разрушая `1,2-Hexanediol`, полимерные названия, дефисы и slash-названия. Объединяй разорванные слова только при обоснованном совпадении. Удаляй инструкции/маркировку без удаления соседнего INCI.

Удали молчаливую реконструкцию неоднозначных фрагментов под конкретный CeraVe-подобный шаблон. Сделай единое решение о статусе совпадения: анализатор не должен заново повышать `suggested` до `found`. Различай Hamamelis Water, Leaf Extract, Bark/Leaf Extract и неопределённый Extract. Торговые комплексы не раскладывать на вымышленные компоненты. Дубликаты не должны терять происхождение/позицию исходного текста.

**Приёмка:**
- Исходный Topicrem из аудита содержит после разбора все 20 отдельных позиций, включая Glycerin и Urea.
- Типовые Nacinamide/Phenoxyethanal и разорванный PEG-40 проходят; сомнительные исправления остаются предложениями.
- `Hamamelis Virginiana Extract` не получает экспертную оценку за другую подтверждённую форму.
- Все смысловые изменения представлены в журнале преобразований; мусор не добавляет ingredients; числовой хвост не уничтожает строку.

## T06. Фото: камера, загрузка, лицевая сторона и состав

**Модель:** Sol high. Причина: связанный сценарий браузера, OCR и получения карточек.

**Задание для Codex:**

Доведи существующую съёмку/загрузку до явной машины состояний: фото принято, чтение, тип этикетки, требуется подтверждение, анализ, ошибка. Сохраняй OCR confidence и координаты, когда движок их отдаёт. `unknown` и случайный текст не должны запускать анализ. По лицевой стороне показывай кандидатов и источник состава; по составу используй очищенные подтверждённые позиции; для смешанной/плохо читаемой фотографии проси уточнение.

Добавь проверку размера/формата, контролируемую отмену старого задания при новом фото или очистке, освобождение камеры/объектных URL. Покажи этапы и прогресс без перекрытия изображения. Не отправляй фото внешнему AI-провайдеру в этом задании. Для обрезки/поворота используй подходящий существующий инструмент, не пиши свой OCR.

**Приёмка:**
- Подменённый ответ `mode:unknown` из аудита никогда не вызывает `/api/analyze` автоматически.
- Очистка фото во время OCR не позволяет позднему ответу восстановить его состав.
- Обе кнопки «Камера»/«Загрузить» работают; отказ камеры предлагает загрузку; поток останавливается при закрытии.
- Реальные ограничения OCR отмечены отдельно от результатов тестов с моками.

## T07. Штрихкоды и допустимые QR

**Модель:** Sol high. Причина: браузерные различия и жизненный цикл камеры.

**Задание для Codex:**

Добавь декодирование EAN/UPC из видеопотока и загруженной фотографии. Используй нативный BarcodeDetector только при поддержке необходимых форматов и поддерживаемую библиотеку-декодер как fallback. Перед выбором зависимости проверь актуальные документацию, лицензию и совместимость. Не реализуй декодер самостоятельно. Проверяй контрольную цифру и допустимую длину; обработай эквивалентность UPC-A/EAN-13 с ведущим нулём явно.

QR обрабатывай только как подтверждённый товарный идентификатор/поддерживаемый формат. Не открывай произвольную ссылку автоматически и не выполняй серверный fetch любого URL из QR. Произвольные длинные числа внутри текста не считать EAN.

**Приёмка:**
- Код распознаётся на тестовом изображении и при отсутствии native BarcodeDetector.
- Некорректная контрольная цифра не приводит к запросу другого товара; один код не запускает десятки одинаковых запросов.
- Есть fallback при запрете камеры, закрытие останавливает поток, поддержаны загрузка и ручной ввод.
- Проверки на физических Android/iOS перечислены отдельно; без устройства не заявлять успех.

## T08. Источники, идентификация и версии формулы

**Модель:** Sol high. Причина: несколько адаптеров, доверие к данным и отказоустойчивость.

**Задание для Codex:**

Исправь основной поиск по штрихкоду: точный `code` не должен отбрасываться из-за отсутствия INCI. По полученной идентичности ищи состав в дополнительных источниках, проверяя модель/вариант товара. Убери возможность прохождения нерелевантной карточки только за бонус «есть состав». Не смешивай разные формулы; сохраняй источник, дату, рынок/вариант, если опубликованы. Передавай конфликты клиенту для T16.

Используй существующие адаптеры. Добавь разумный TTL, кратковременный negative-cache, таймауты и различимые статусы not_found/no_inci/unavailable. Уважай условия и ограничения источников. Кэшируй только запрошенные товары. Не создавай произвольный URL-fetch для пользователя или открытый прокси.

**Приёмка:**
- Точный EAN карточки без состава сохраняется как идентифицированный товар, а не «не найдено».
- Состав не может перевесить полное отсутствие совпадения бренда/модели.
- Две версии сохраняются раздельно и доходят до клиента с источниками; ошибки источника не равны отсутствию товара.
- Есть детерминированные тесты адаптеров и отдельно необязательный live smoke-test; CI не зависит от доступности сайтов.

## T09. Удаление ложной точности

**Модель:** Terra high. Причина: локальное приведение расчётов и отображения к уже заданным ограничениям, без создания новой методики.

**Задание для Codex:**

Прекрати выдавать фиксированные 6/10 за факт нахождения в CosIng, общий балл при недостатке сведений и предполагаемую границу 1% по номеру ингредиента. Не заменяй их другой придуманной формулой. Возвращай `not_assessed`/`null` с причиной по контракту T04. Согласуй минимальные изменения renderer и истории, чтобы null не превращался в 0/100, NaN или пустое «качество».

**Приёмка:**
- Registry-only состав не получает экспертного качества и нулевого «риска» как подтверждения безопасности.

- Список только активов не оценивается как вся формула.
- Название «качество сырья» не используется без данных о сырье; объяснение ограничений видно пользователю.

## T10. Доказательная база и правила анализа

**Модель:** Astra high. Причина: главная логика продукта и границы допустимых выводов.

**Задание для Codex:**

Раздели справочник идентичности INCI и экспертные утверждения. Спроектируй и реализуй в текущих модулях схему проверяемых утверждений: роль, возможный вклад, условия применимости, ограничения, ссылка на источник, дата проверки, версия, статус предметного ревью. Отсутствие данных не должно превращаться в отсутствие риска. Сопоставь функции CosIng с внутренними группами без автоматического присвоения экспертной доказанности.

Утверждения о концентрации/pH/SPF требуют данных готового продукта. Создай небольшую проверяемую стартовую выборку; не заполняй тысячи статей генерацией. Документируй приоритеты правил и способ расширения. Не добавляй runtime-LLM как замену правилам.

**Приёмка:**

- Правила детерминированы, версионируются, покрыты положительными/отрицательными тестами.
- Неотсмотренные предметным специалистом утверждения явно помечены и не становятся жёсткими медицинскими рекомендациями.

## T11. Воспроизводимый импорт INCI

**Задание для Codex:**

Обнови импортёр локального registry по схеме T10. Сохраняй происхождение, доступную версию/дату выгрузки, URL и проверочную сумму. CAS, aliases, функции и ограничения добавляй только когда они действительно есть в источнике. Не выдумывай пропущенные значения и не представляй зеркало старого CSV как прямой live-запрос в CosIng. Раздели импортные данные и локальные подтверждённые дополнения. Обновление должно быть атомарным, с отчётом diff и возможностью использовать предыдущую корректную версию.

## T12. Полезное экспертное покрытие

**Задание для Codex:**

Составь приоритет расширения базы по частоте ингредиентов в доступных реальных составах, а не по желанию получить красивое число записей. Проверь нынешние 122 записи на источники, противоречия и слишком сильные обещания. Работай партиями до 25 ингредиентов: роль, эффекты с условиями, риски, ограничения применимости, ссылки и дата. Используй первичные/официальные источники; товарное описание не доказывает универсальное свойство вещества. Не заполняй пробелы генерацией текста.

**Приёмка каждой партии:**
- Валидные записи, действительные источники и явный статус «проверено/требует предметной проверки/недостаточно данных».

## T13. Тип и назначение продукта

- Назначение и инструкция имеют источник либо явно помечены как гипотеза; не генерируется схема лекарственного применения.

## T14. Персональная оценка

**Задание для Codex:**

Предусмотри тип/состояние кожи, цели, подтверждённые аллергии, область применения, реакцию на прошлые средства, контекст процедур и иные необходимые признаки с минимизацией чувствительных данных. Не диагностируй болезни и не выводи их из фотографии.

Подключи проверенные правила T10/T12: сначала противопоказания/несовместимость, затем предосторожности, затем потенциальная польза. Непроверенные клинические правила не превращай в назначения. Согласуй рекомендации с классом T13. Важное предупреждение не может исчезнуть из-за лимита длины или сосуществовать с противоположным советом «начните применять». При недостаточном профиле показывай ограничения персонализации. Без отдельного согласия не добавляй новые чувствительные поля в долговременное хранение.

- В safety-сценариях отсутствуют одновременно запрет и совет начать применение; важные предупреждения не обрезаются.
- В отчёте видны фактически учтённые признаки и причины; отсутствие сведений не означает подтверждённую безопасность.

## T18. Испытания на реальных данных

**Модель:** Sol high. Причина: сквозная автоматизация, реальные внешние зависимости и измерение качества.

**Задание для Codex:**

Собери воспроизводимый эталонный набор фото/текстов/штрихкодов из разрешённых материалов. Цель: минимум 100 разноплановых этикеток, но не выдумывать примеры и не заявлять, что набор собран при нехватке данных. Включи длинные INCI, мелкий шрифт, блики, изгиб упаковки, лицевую сторону, только активы, разные языки, неизвестные товары и не-косметические средства. Эталон независимо проверяется человеком по источнику, а не генерируется самим тестируемым анализатором.

Раздели настройку и финальный тест по товарам/брендам. Измеряй отдельно точность/полноту извлечения, идентификацию товара, экспертное покрытие, правильность отказа и противоречия рекомендаций. **Модель:** Astra high, при необходимости xhigh. Причина: проверить не красивый отчёт, а согласованность всей системы и попытаться опровергнуть готовность.

**Приёмка:**
- Итог `готов к ограниченному тестированию / не готов`, с обоснованием и перечнем недопроверенного.

- Деплой не выполняется автоматически.

## T20. Аналоги: отдельный следующий этап

**Модель:** Sol high. Не блокирует первый выпуск качественного разбора.

**Задание для Codex:**

После положительной T19 доработай аналоги. Сначала фильтруй по назначению, зоне, смываемости, ограничениям человека и достаточности состава, только затем считай сходство. Не называй продукт идентичным только из-за пересечения INCI. Не рекомендуй demo-карточки. «Дешевле» допустимо только при реальной сопоставимой цене/объёме с датой и источником; доступность в РФ не определять по бренду или подстроке `ru`.

**Приёмка:**
- Уходовый крем не заменяется пилингом/шампунем/процедурным препаратом из-за общих компонентов.
- Неизвестные цена/наличие помечены неизвестными; рекомендации содержат объяснение совпадений и различий.
- Ограничения человека проверяются до ранжирования; неполная формула не выглядит полноценной заменой.

## Что не отдавать модели как безусловное полномочие

- Подтверждение противопоказаний и лечебных рекомендаций без источников и предметной проверки.
- Вычисление качества сырья, реального SPF, pH и процентов по порядку INCI.
- Восстановление плохо читаемых ингредиентов «по похожему продукту» без обозначения догадки.
- Обещание найти любой продающийся товар или гарантировать индивидуальную переносимость.
- Выбор платного production AI-провайдера на основании того, какая модель лучше пишет код.

Приоритет результата: **правильный состав -> достоверный подробный разбор -> согласованная персональная оценка -> удобный интерфейс -> аналоги**. Масштабирование каталогов не должно опережать исправление ошибок этой цепочки.
