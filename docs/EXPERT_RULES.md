# Проверяемые правила анализа (T10)

## Границы данных

- `data/inci-registry.json`: идентичность и справочные функции. Не доказывает
  эффективность, безопасность, качество сырья или назначение продукта.
- `data/expert-claims.json`: отдельная небольшая база утверждений со ссылками.
  Четыре записи, все `pending`. Прочитанные аннотации исследований
  не означают предметное ревью или систематический обзор литературы.
- `data/ingredients-expert.json`: старый словарь. Анализатор и очиститель пока
  используют его названия/aliases, а существующая классификация также категории
  и роли. Его `benefits`, `risks`, `best_for`, `avoid_for`, `quality_score`,
  `evidence_level` больше не являются экспертным основанием отчета.
  Импорт и миграция всего справочника относятся к T11/T12, не к T10.

## Схема утверждения

`schemaVersion` описывает схему файла, `version` версионирует весь набор.
Каждый claim содержит:

| Поле | Назначение |
| --- | --- |
| ruleId | Стабильный идентификатор правила |
| version | Версия смысла конкретного утверждения |
| ingredient | Точное каноническое имя из локального registry |
| role | Обсуждаемая роль компонента |
| possibleContribution | Осторожный вывод в пределах источника |
| conditions | Проверяемые условия: applicationSite, usage, concentrationPercent, productForm |
| riskAssessment | Отдельный статус, проверяемые сведения о риске и ограничения; пустой источник не превращается в «риска нет» |
| limitations | Обязательные ограничения переноса результата |
| basis | sourceId и locator (раздел первичного источника) |
| checkedAt | Дата проверки содержания источника, не клиническое одобрение |
| evidenceStatus | verified/review_required/insufficient_data |
| review | pending/approved/rejected; для approved обязательны reviewer и reviewedAt |

Sources содержат URL, название, тип, дату и объем проверки, контекст исследования.
Схема 1.1 поддерживает только первичные исследования, проверенные по аннотации.
Для иных типов источников надо явно расширить схему и тесты, а не обозначать их
этим типом. Отсутствующая запись или нарушенная схема не заменяются старой базой:
загрузка ошибочного набора завершается ошибкой.

## Приоритеты

1. Ограничения доказательности действуют всегда: нет числового риска или
   эффективности без валидированной методики и данных готового продукта.
2. Некосметическая классификация отключает косметические экспертные выводы.
   Существующая эвристика сохраняется, но помечается `unreviewed_heuristic`;
   ее прежние инструкции применения не выдаются как рекомендации.
3. Suggested/unknown и закрытые комплексы не получают функций/свойств по
   предполагаемому имени. Исходные имена сохраняются.
4. Подтвержденная идентичность позволяет показать функции локального registry
   как `kind: reference`. Явная таблица маппинга не добавляет лечебных свойств:
   SKIN CONDITIONING не означает доказанное восстановление барьера; HAIR
   CONDITIONING не означает, что данный товар предназначен для волос;
   UV FILTER не дает значение SPF. Неизвестная функция остается `unmapped`.
5. Только точное каноническое имя подключает литературное утверждение.
   `rejected` не выводится; `pending` явно подписано «Требует предметного ревью».
6. Недостающие условия дают `conditional`, конфликтующие `not_applicable`.
   Даже `approved` + `context_matches` не доказывают эффект данного продукта:
   `productEffectConfirmed` остается false. Никаких медицинских схем назначения.

Условия описывают применимость исследования, а не извлеченные из INCI проценты.
`evaluateExpertRules` умеет сравнивать явно переданный контекст; публичный анализ
пока не принимает его за проверенный и вызывает движок с пустым контекстом.
Поэтому применимость стартовых исследований в обычном отчете условная.
Классификатор/профиль не заполняют неизвестные концентрации и параметры продукта.
Проверенные измерения готового продукта еще не подключены: concentration, pH,
SPF, efficacy, irritationRisk, rawMaterialQuality всегда `not_assessed`.

## Выход и воспроизводимость

- `findings[]`: ruleId, version, kind, text, basis, review; у литературных
  утверждений также условия, limitations и результат их проверки.
- `found[].findings`: основания по каждому распознанному компоненту.
- `groups`/`architecture`: справочные группы с ruleId, без баллов эффективности.
- `expertSummaryRuleIds`: связь старого текстового поля сводки с findings.
- `evidenceCoverage`: различает идентифицированные имена, наличие литературной
  записи и наличие утверждения с предметным ревью. Это счетчики, не вероятность.
- `evidenceVersions`: версия движка, версия знаний, SHA-256 базы утверждений и
  локального registry. Сохраняется также в `analysisContract`.
- `finishedProductAssessment`: явные неоцененные параметры и причина.

Одинаковые входы и файлы дают одинаковый результат. Runtime не ходит в сеть,
не вызывает LLM и не назначает текущую дату проверки автоматически. Разрешение
идентичности остается задачей существующего INCI pipeline. Старые поля API
сохраняются; числовые оценки null; текстовые поля строятся из нового разбора.
Алгоритм контракта: `analyzer-v5-personal-context`. Старые контракты без evidenceVersions
остаются валидными. Миграции сохраненной истории не выполнялись.

Для reference-оснований указан локальный файл, каноническая запись, исходная
функция, SHA-256 и метаданные импорта. T11 добавил построчное происхождение и
отдельные локальные aliases. Текущий снимок помечен как legacy mirror: у него
честно `null` для даты/версии экспорта, CAS, ограничений и номера исходной
строки. Это не live-проверка CosIng. Наличие вещества в CosIng само по себе не
разрешает его использование и не подтверждает безопасность: [пояснение Еврокомиссии](https://single-market-economy.ec.europa.eu/sectors/cosmetics/cosmetic-ingredient-database_en).

## Расширение

1. Выбрать каноническое имя, изучить первичный источник, указать точный раздел,
   популяцию, исследованную формулу, пределы вывода и дату проверки.
2. Добавить source и claim со статусом pending. Не переносить дозировку или
   процент исследования в текущий продукт. Не давать баллы «качества» из памяти.
3. Проверить положительный случай, неподтвержденное имя, отсутствие контекста,
   конфликт контекста, отзыв утверждения и сохранение null для параметров продукта.
4. Предметный специалист проверяет формулировку, ограничения и источники;
   только после этого записываются реальный reviewer и reviewedAt.
5. При изменении смысла обновить claim.version и общую version; при изменении
   приоритетов/маппинга увеличить EXPERT_RULES_VERSION и версию алгоритма.
6. Выполнить `npm.cmd run test:t10`, `npm.cmd test`, `npm.cmd run check`.
