# Схема экспертных знаний C05

Версия файла: `2.0`. Реализация: `src/services/expertKnowledge.js`, подключение: `src/services/expertRules.js`. Основание: контракт C01 в `FORMULA_ASSESSMENT_SPEC.md`.

## Границы

Это формат источников, утверждений, применимости и ревью. Он не добавляет новые научные сведения, регуляторные пределы, оценки качества, персональные советы или измерения продукта. В production сохранены четыре прежних утверждения, все `pending`. Реестр людей `reviewers` пуст.

`conclusionSupported` означает, что тип и объект источника допустимы, обязательный контекст совпал, нет нерешённых причин неизвестности и имеется структурно корректная предметная подпись. Это не универсальная истинность текста, не доказательство безопасности и не разрешение применять продукт. `productEffectConfirmed` остаётся `false`; заполнение измерений продукта относится к последующим заданиям.

## Источники

Общие поля: `id`, `url` или `artifactRef`, `title`, `type`, `checkedAt`, `checkedScope`, `context`, `version`, `retrievedAt`, `publishedAt`, `contentHash`, `subject`, `conditions`.

Неизвестные версии, даты публикации/загрузки и хеш содержимого имеют значение `null`. Дата проверки не становится датой публикации. `artifactRef` обозначает разрешённый локальный архив в `artifacts/`, документ в `reviews/` или HTTPS-ссылку; валидатор не загружает произвольные URL. Для предметно одобренного правила нужен сохранённый источник с хешем содержимого либо ссылкой на архивный артефакт.

| type | checkedScope | Допустимый conclusionType |
| --- | --- | --- |
| primary_study_abstract | abstract_only | literature_observation |
| study | full_text | literature_observation, technical_property |
| review | full_text | literature_observation, technical_property |
| regulatory_document | full_text, relevant_section | regulatory_restriction |
| technical_document | full_text, relevant_section | technical_property |
| product_test | full_report | product_test_result |
| ingredient_reference | record | ingredient_identity, reference_function |
| manufacturer_page | product_page | manufacturer_declaration |
| package_label | label | manufacturer_declaration |
| third_party_catalog | record | catalog_report |

Каждый элемент `basis` обязан соответствовать этой матрице. Каталог, реклама или аннотация не становятся протоколом испытания. `riskAssessment.status: assessed` разрешён только при источниках `study`, `review` или `product_test`; сами утверждения о риске всё равно требуют предметной проверки.

`regulatory_document` дополнительно содержит `regulation: {jurisdiction, version, effectiveFrom, effectiveTo}`. Окончание срока может быть `null`. У правила обязательны соответствующие `conditions.jurisdiction` и `conditions.regulatoryVersion`; при оценке нужна явно заданная `assessmentDate`. Дата системы не подставляется. Эти поля позволяют проверить область применимости документа, но не подтверждают правовой статус товара.

`product_test` требует `method` и точную версию `finished_product`. Наличие красивого названия или состава не заменяет идентификацию испытанного образца.

## Объект утверждения

`subject: {kind, id, formulaVersion}` одинаков у источника и каждого основанного на нём утверждения:

- `substance`: `id` совпадает с каноническим `ingredient`, `formulaVersion: null`.
- `studied_formula`: локальный идентификатор исследованной формулы, версия может быть неизвестной (`null`). Неизвестная версия всегда оставляет применимость условной.
- `finished_product`: точный идентификатор формулы и непустая версия.

`ingredient` остаётся ключом поиска литературы при разборе INCI, но не меняет объект вывода. Например, карточка Panthenol может ссылаться на наблюдение над `studied_formula`; это не утверждение об изолированном пантеноле. Три существующих источника получили локальные `study:pmid-*` идентификаторы, а версии формул оставлены неизвестными. Новые продуктовые факты при миграции не создавались.

## Применимость

`conditions` поддерживает `applicationSite`, `usage`, `productForm`, `productType`, `jurisdiction`, `regulatoryVersion`, `concentrationPercent`. Тип и форма продукта сравниваются по точному значению. `skin` включает `face`/`body`, но не `hair`. Неизвестные/пустые значения не считаются совпадением.

У источника также есть `conditions`. Правило обязано сохранить все эти ограничения; концентрационный диапазон можно сузить, но нельзя расширить. Это позволяет документировать контекст источника отдельно от контекста правила.

`concentrationPercent` правила: точное число или `{min, max}`, границы включены. Для проверки движку требуется:

```json
{
  "concentrations": {
    "Glycerin": {
      "subjectKind": "substance",
      "subjectId": "Glycerin",
      "value": 3,
      "unit": "percent",
      "verification": "source_checked",
      "sourceId": "example-source-id"
    }
  }
}
```

Это синтетический пример структуры, не состав товара и не норматив. Число из общего `context.concentrationPercent`, процент торговой смеси, строка или значение `user_reported` не дают подтверждения. Публичный API не принимает этот объект как проверенное измерение: он предназначен для будущей серверной интеграции источников.

Для `studied_formula`/`finished_product` дополнительно сравниваются `context.formulaId` и `context.formulaVersion`. Совпадение одного ингредиента или категории недостаточно.

Выход: `context_matches`, `conditional` или `not_applicable`, списки `missing` и `conflicts`, `unknownReasons`, `conclusionSupported`. Явные причины неизвестности из базы и отсутствующие условия сохраняются. При `insufficient_data` обязательна хотя бы одна причина. Наличие `unknownReasons` не позволяет положительное подтверждение, даже если остальные поля совпали.

## Предметная подпись

`pending` не повышается автоматически. Для `approved` обязательны:

1. Запись `reviewers[]` с `id`, `kind: human`, именем, квалификацией и `verification: {verifiedBy, verifiedAt, artifactRef}`.
2. `review` с `reviewerId`, совпадающим именем `reviewer`, датой `reviewedAt`, `claimVersion`, `artifactRef` реального заключения и `contentHash`.
3. `evidenceStatus: verified`, сохранённые источники и совпадающий хеш правила вместе с метаданными его источников.

`reviewContentHash(claim, sources)` вычисляет подпись содержимого; изменение текста, условий, объекта или источника делает старый хеш недействительным. Это контроль целостности данных, не криптографическая подпись человека. Проверку личности, квалификации, существования и содержания заключения выполняет ответственный редактор до внесения записи. Валидатор не способен удостоверить реальность человека по строке JSON. Знания загружаются только из серверного файла; review-поля клиента не используются.

Фикстуры `TEST FIXTURE ONLY` находятся только в `tests/` и не являются предметным ревью. В рабочей базе нет созданных моделью человеческих подписей.

## Отзыв и версии

`lifecycle: {status, changedAt, reason, replacedBy}`:

- `active`: доступно при соблюдении остальных ограничений.
- `withdrawn`: не попадает в новый анализ; причина обязательна.
- `superseded`: не попадает в новый анализ; нужна причина и ссылка на существующее активное правило.

`versionHistory` хранит версии, даты изменения, описание изменения, снимок семантического содержимого, `contentHash` и `previousHash`. Последняя запись обязана совпадать с текущим правилом. Снимок исключает саму историю и подпись, чтобы избежать рекурсивного хеширования. Смысловые изменения требуют новой версии и новой проверки подписи. Цепочка позволяет обнаружить несогласованное редактирование, но не защищает файл от лица, способного переписать и данные, и все хеши; контроль изменений обеспечивает git и редакционный процесс.

Сохранённый отчёт содержит исходные findings, источники и версии. Чтение истории не запускает новые правила: отзыв действует при новом анализе, старый снимок остаётся историческим. Пересчёт создаёт новый результат. Схема API и история не мигрируются.

Файлы знаний `1.1` структурно читаются для совместимости, но при новом запуске их экспертное подтверждение требует миграции: `conditional`, `review_required`. При открытии старого сохранённого отчёта его выводы не переинтерпретируются.

## Обслуживание

`node scripts/migrate-c05-knowledge.mjs` воспроизводимо переносит известный pending-набор 1.1 в 2.0. Повторный запуск ничего не меняет. Миграция не читает новые публикации и не подставляет отсутствующие даты/версии. Для нового набора/одобренных записей требуется отдельное рассмотрение миграции.

`npm.cmd run test:c05` проверяет матрицу источников, неизвестность и конфликты контекста, невозможность переноса результата между формулами, подписи, отзыв и совместимость истории. Добавление предметных записей относится к C06; системный разбор и измерения продукта к C07-C10.
